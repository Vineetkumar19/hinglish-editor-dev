01 The hardware gap — read this first

Every one of the eight specifications you attached — and the "Claude Max 1-Month Build Playbook" that ties them together — is written against an RTX 4080 Laptop, 12GB VRAM, high-end HX CPU, 32–64GB RAM. That machine can keep an 8B–14B model resident in VRAM, run a vision model alongside it, and process video locally without the GPU becoming the bottleneck.

What you actually have

Ryzen 5 4600H, GTX 1650 4GB, 24GB RAM — currently running qwen2.5:3b on CPU because 4GB VRAM can't hold anything bigger without the CUDA crashes you already hit with qwen3:8b. This is not a smaller version of the same plan. It's a different machine class, and the playbook's assumptions about "the model reasons, tools execute instantly, vision runs continuously" don't hold when reasoning itself takes 3–5 seconds per turn.

This doesn't mean the vision in these documents is wrong — the architecture (Cortana Core as boss, specialist agents, deterministic tools, permission ladder, shared memory) is sound and is exactly what the current Cortana already implements in miniature. It means scope and sequencing have to change, and a few capabilities need to be marked honestly as "not viable on this hardware" rather than silently built badly.

What changes, concretely

CapabilityPlaybook assumptionReality on your laptop

The good news — this is already anticipated

The current Cortana has a cloud_fallback module (built last session, off by default) that lets any turn escalate to a cloud-hosted model over an OpenAI-compatible endpoint when local inference genuinely isn't enough — exactly the "optional cloud escalation, not a promise of 100% local frontier intelligence" the playbook itself recommends. The Developer Agent and anything doing multi-file reasoning is where you'll actually want to turn it on.

02 System architecture

All eight specs agree on one shape: Cortana Core is the only orchestrator; everything else is a specialist that requests routing through it rather than acting independently. That's already true of the running system — chat.py is the single entry point, the tool registry is the single dispatch point, and every tool goes through the same permission check. The extension below keeps that shape and slots the new domains in as siblings, not replacements.

Why "shared platform" is its own layer, not part of each agent

The Communication/Vision spec says this explicitly and it's the single most important structural decision in all eight documents: "Do not give every specialist its own independent mouse, keyboard, browser and screen-control implementation." Right now, if Career needs to click through a job application form and Content needs to open a Premiere project and Communication needs to open WhatsApp Web, all three need the same underlying "open a window, click a thing, verify it happened" primitives. Build that once as a Computer Control tool family, and every specialist calls it — don't let three agents grow three different Playwright wrappers.

03 Permission ladder — one system, not eight

Every spec independently invents a permission ladder with slightly different names (READ→ANALYZE→DRAFT→CONFIRM→EXECUTE in Finance/Career, OBSERVE→ANALYZE→DRAFT→CONFIRM→EXECUTE→VERIFY in Communication/Security). They're the same idea. Rather than building six different permission systems, collapse them onto the RiskLevel enum already in core/permissions.py, extended with the stages as sub-states of the HIGH tier:

StageExisting RiskLevelMeaningExample
OBSERVELOWRead-only, no side effectsread_pdf, take_screenshot, search_files
ANALYZELOWReasoning over already-read datascore_job, detect anomaly, classify email
DRAFTMEDIUMProduces something a human reviews before it goes anywherecompose_email, tailor_resume, prepare calendar event
CONFIRMHIGHNeeds explicit yes before the next stage — currently fails closed because no confirmation UI exists yetsend_message, submit_application, install_dependency
EXECUTEHIGH, post-confirmationThe consequential action itselfactually clicking Send, actually submitting
VERIFYnew — runs after any EXECUTEProves the action really happened, doesn't trust its own success claim"was the email actually sent", "does the window exist now"
—CRITICALAlways blocked, no exceptionsshell exec, delete, format, registry edit — already permanently barred
One real gap to close before CONFIRM-tier tools go live

Today, Decision.NEEDS_CONFIRMATION fails closed because there's no UI for the user to actually confirm anything — it's a placeholder. Before Career (submit_application), Communication (send_message), or Automation (execute_workflow) go live, the desktop app needs a real confirmation modal: show the exact action, wait for click, then dispatch. This is small (a React modal + one new endpoint) but it's a hard prerequisite for roughly half the new capabilities in these specs.

04 Memory model

The Knowledge spec defines seven memory types. The current memory_facts table is flat — one bucket, lexically searched, no domain isolation. That was fine for "remember my sister's birthday." It's not fine once Finance, Career and Developer all want to store things and none of them should leak into each other's context.

memory_facts (extend, don't replace)
┌────────────────────────────────────────────────────────────┐
│ id · content · category            (existing)                │
│ + domain        global | developer | content | career |     │
│                  finance | communication | security          │
│ + scope_id       NULL for global, else project/repo/campaign │
│                  id this fact belongs to                     │
│ + source         where this came from (user told me /        │
│                  extracted from doc X / inferred)             │
│ + confidence     stated | inferred | uncertain                │
│ + sensitivity    normal | sensitive | secret-adjacent          │
│ + expires_at     NULL = permanent, else episodic TTL           │
└────────────────────────────────────────────────────────────┘

Retrieval rule: recall_facts always filters by domain first.
A Developer-agent turn never sees Finance-domain facts unless
the user explicitly asks Cortana Core to cross-reference them.

This is a schema migration, not a rewrite — db.py's existing add_fact/recall_facts/retrieve_relevant functions gain a domain filter parameter and three new columns. Small, and it should happen before the Developer or Finance agents are built, because retrofitting domain isolation after two agents are already sharing one memory pool is much more disruptive.

Here's that classification applied with your actual hardware and the "smallest reliable stack" principle in mind. Full repo details are in your uploaded research doc; this is the decision layer on top of it.

Verdicts favor STUDY over WRAP/REUSE almost everywhere because most of these repos assume either continuous GPU-hungry inference or a full separate service stack — on this hardware, re-implementing the pattern as a lightweight tool inside the existing FastAPI agent is usually cheaper than integrating someone else's service. Browser Use is the clear exception: genuinely worth wrapping directly.

06 Build roadmap

Not "Month 1." The playbook's 4-week schedule assumes a team-scale Claude Max budget driving parallel workstreams on capable hardware. Working solo, step by step, on this hardware, the honest unit is phases with real acceptance tests, done in dependency order — platform pieces that everything else needs, first.

Phase 0 — Confirmation UI + Memory domainsprerequisite
  • Build the confirmation modal in the desktop app + a real /api/confirm flow, so HIGH-risk tools stop failing closed.
  • Migrate memory_facts to the domain-scoped schema in §04.
Blocks: Career (submit), Communication (send), Automation (execute) — all of which need real confirmation to be usable at all.
Phase 1 — Computer Control Layershared platform
  • Window focus/switch/minimize/close (extends tools/apps.py).
  • Verification primitive: "does this window now exist" — the shared check every later agent calls after an action.
  • Clipboard read/write.
Builds on: existing open_application/open_folder. Blocks: every later agent that needs to control an app, not just launch it.
Phase 2 — Browser control (wrap Browser Use)shared platform
  • Read page content, click elements, fill forms — the gap tools/web.py currently has.
  • Structured-first: prefer an API/connector when one exists, browser automation as fallback (the spec's own stated preference).
Builds on: Phase 1 verification pattern. Blocks: Career (apply), Instagram (outreach), Entertainment (search+play).
Phase 3 — Document Agent, generation halfshared platform
  • PDF/DOCX → PPTX, PDF tables → XLSX (extends the existing read-only tools/documents.py).
  • Versioned output, never overwrite source — already the pattern used elsewhere in the codebase.
Builds on: existing document reading. Independent of Phases 1-2 — can run in parallel if you want a break from browser/window plumbing.
Phase 4 — Developer Agent V1 (narrow)specialist
  • Repository map (language/framework detection, entry points) — not a full AST/language-server layer yet.
  • Single-file, tool-verified patches: understand → patch → run narrowest test → show diff.
  • Cloud escalation wired in explicitly for anything touching more than ~2 files — this is where cloud_fallback.py earns its place.
Builds on: Phase 0 confirmation (git commit/push gates), Phase 1 (running dev servers, opening IDE).
Phase 5 — Communication + Calendarspecialist
  • Extends the existing draft-and-handoff pattern in tools/communication.py to WhatsApp/Telegram/email triage.
  • Relationship-aware tone (needs the domain-scoped memory from Phase 0 to store contact profiles safely).
  • Calendar create/check availability — currently only create_calendar_event exists as a URL handoff; needs real read access to check conflicts.
Builds on: Phase 0 memory domains, Phase 0 confirmation for sending.
Phase 6 — Career Agentspecialist
  • Discovery + dedup + freshness tracking (own schema, per spec §4).
  • Match scoring with explainable sub-scores.
  • Resume tailoring with the requirement→evidence matrix — this is the safeguard against fabrication and should be built before generation, not after.
  • Application prep stops at CONFIRM; submission is Phase 6b once the whole pipeline has been trusted for a while.
Builds on: Phase 2 (browser for applying), Phase 3 (PDF generation for tailored resumes), Phase 0 (confirmation before submit).
Phase 7 — Finance Agent V1 (read-only)specialist
  • Net worth, manual/CSV portfolio import, monthly review — no live connectors yet.
  • Deterministic calculation engine kept entirely outside the LLM, per the spec's explicit rule.
Builds on: Phase 3 (CSV/XLSX import), Phase 0 (memory domain for finance facts, kept strictly isolated).
Phase 8 — Instagram Content Agentspecialist
  • Analytics on your own account history first (evidence over prediction, per spec).
  • Creator CRM-style brand outreach pipeline, gated at CONFIRM before any pitch is sent.
Builds on: Phase 2 (browser for Instagram web), Phase 5 (outreach messaging pattern).
Phase 9 — Content/Video Agentspecialist · largest single phase
  • Whisper transcription → silence/filler detection → cut ranges → captions (all CPU-viable today).
  • FFmpeg-based render pipeline, not an LLM touching every frame.
  • Motion templates as parameterized configs, not generated-per-video.
  • Deliberately scoped last — it's the single heaviest subsystem in all eight specs and deserves its own multi-week block once everything it depends on (Document Agent for reports, Communication for "here's your render") already exists.
Builds on: almost everything before it, which is exactly why it's last.
Phase 10 — Security + Automationhardening
  • Secret scanning, permission inventory ("what can Cortana access"), backup health check.
  • Workflow engine: dry-run → approve → schedule → verify, for the repeated tasks that emerge naturally once Phases 1-9 exist to automate.
Deliberately last — automation needs real workflows to automate, and those only exist once the specialist agents are built.

07 Non-negotiables, consolidated

Every spec repeats variations of the same handful of rules. Collected once, so they don't need re-deriving per phase:

No arbitrary execution

No shell/eval/run_command tool, ever — already enforced by the ForbiddenTool tripwire in the existing registry.

No fabrication

Resume facts, financial figures, follower counts, brand relationships — if there's no verified evidence, the output is a gap, not a guess.

Deterministic where possible

Finance math, video QA, resume ATS checks — code computes, the LLM explains. Never the reverse.

Domain memory isolation

Finance facts never leak into a Developer or Content conversation by default (§04).

Consequential actions need a human

Send, submit, install, delete, push, trade — all stop at CONFIRM until Phase 0's real confirmation UI exists, and stay there by default afterward.

Verify, don't trust

Every EXECUTE is followed by a check that the thing actually happened — not just that the tool call returned without error.

Untrusted content stays untrusted

A README, webpage, email or resume can contain injected instructions. Retrieved text is data, never a higher-priority instruction.

Respect platform terms

No CAPTCHA/MFA bypass, no scraping past a platform's stated limits, no personal-proxy routing through a provider's free tier without knowing its terms — the same standard already applied to the OmniRoute decision last session.
